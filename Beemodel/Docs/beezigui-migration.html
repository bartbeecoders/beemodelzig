BeeZigUi in BeeModel: migration plan

How every part of BeeModel's user interface moves onto BeeZigUi (Zui, ../BeeZigUi), one step at a time, with the app working and all scenarios passing after each step. Written 2026-11-14, after the folders were reordered into BeeModel/Beemodel and BeeModel/BeeZigUi. The Docs/zui-pilot.md pilot (Preferences drawn by Zui behind -Dzui=true) is the starting point.

Goal and scope

Goal. Every widget, panel, menu, dialog, list, area and editor frame in BeeModel is described with Zui. BeeModel's own UI layer (ui.zig widgets, wg.zig, kbnav.zig, menus.zig, pies.zig, dialogs.zig, the area code in app.zig, and the hand-drawn rows in every panel) is deleted at the end.

What moves to Zui: widgets and layout, tooltips and disabled reasons, keyboard focus, menus, the F3 palette, pies and the wheel, dialogs and forms, toasts and the status bar, lists, trees and tiles, text views and the console, the colour picker, the file browser, areas, docking, workspaces and floating panels, the chrome of the 2D editors (rulers, playhead, handles, box select, pan and zoom), and the node editor.

What stays BeeModel's, as Zui's own plan already says: the 3D rasterizer and path tracer and what they draw (grid, meshes, gizmo, overlays, sculpt and paint cursors); the content of the 2D editors (keys, curves, UVs, the render result, node graphs), which BeeModel now paints through a Zui canvas; the operator catalog and its 692 commands; keymaps; theme data; modal G / R / S; the scene. For now, also the Wayland window (see D4).

Target architecture

One zui.Ui for the main window, owned by a new src/zuihost.zig (grown out of zuiprefs.zig). BeeModel keeps its window, event loop and framebuffer; Zui draws into that framebuffer with its software renderer, in place, exactly as the pilot does today.

1 · Wayland eventwayland.zig + keyboard.zig (XKB, dead keys, layout-aware shortcuts)
2 · Modal firstplay mode, G / R / S, UV and mesh-op modals keep the input while they run
3 · Into Zuizuihost.input: pointer, buttons, wheel, keys, text, file drops onto ui.input
4 · Frameui.beginFrame → the shell (dock, bars, menus) → each area's editor → ui.endFrame
5 · Contentviewport and 2D content painted into canvases / images before or inside the Zui pass
6 · Presentsoftware renderer into the shm buffer; ui.cursor, redraw_in to the Wayland loop
  • One pass instead of two. BeeModel runs app.frame as a hit pass on each event and as a draw pass per frame. Zui queues input and runs one frame. While mixed (M1 to M7), BeeModel's hit pass skips any rect Zui owns: an event goes to Zui first, and BeeModel's own code sees it only when Zui did not take it (ui.wantsKeyboard(), the pointer not over a Zui widget, window or popup). From M7, when the shell is Zui's, the hit pass is gone.
  • Mixed frames are safe. A Zui region (ui.beginRegion(id, rect, …)) can sit inside an area that BeeModel's shell still lays out, so panels move before the shell does. The pilot proved Zui and BeeModel can share one canvas and one frame.
  • A BeeModel panel kit (src/bkit.zig) on top of Zui holds what every panel repeats: section (collapsing header with BeeModel's look), opButton (a catalog operator: label, icon, shortcut, tooltip from the catalog's docs, greyed with the catalog's "Not now: why"), property rows (label + number field with expr.zig as the evaluator, units), and the Properties tab strip. It replaces editors.section, opButtonL and the many local row helpers.
  • Look from BeeModel's data. Zui style from the active theme (styleFrom, from the pilot) for all nine themes, the accent and the colour-blind option; Noto Sans and Noto Sans Bold, mono for the console; BeeModel's 114 icons registered as a Zui icon set; 22-unit rows.
  • Per-area state stays BeeModel's, keyed by Zui's AreaId: a viewport's camera View (read by BeeScript and MCP), a timeline's range, an outliner's filter.
  • Floating panels in their own OS windows (panelwin.zig): Zui windows with .detached = true; panelwin.zig opens an xdg_toplevel per entry of ui.viewports() and feeds back size and input.

Decisions

Recommendations; change any of them before the milestone that depends on it starts.

#DecisionRecommendation and why
D1Zui as a dependencyA path dependency in a new build.zig.zon (.zui = .{ .path = "../BeeZigUi" }) using Zui's own modules (zui, zui_software, zui_nodes, zui_files), instead of build.zig building Zui's source files by path. One place to change, and Zui's add-ons come for free.
D2The -Dzui flagRetire it in M0: Zui becomes required. Keeping both UIs for every panel would double the work over ~30,000 lines. Each step instead replaces a panel's old code in the same change, once its scenarios pass on the new one. The plain build stays reproducible from the last version before M0.
D3Order of workInside out: host and look, then panels made only of widgets (most code, least risk), then lists, menus, text, feedback, and only then the shell (docking), the 2D editors and the viewport. Each milestone delivers a working app.
D4The windowKeep BeeModel's wayland.zig through M9; it already works, and the pilot shows Zui fits inside an app that owns its window. In M10, decide whether to switch to zui_wayland (removes ~1,000 lines of BeeModel; needs the GPU helper's present path and BeeModel's tablet and wlext extensions checked first).
D5Icons and themesBeeModel's 114 icons and nine themes stay in BeeModel (its own source: src/icons.zig, src/themes.zig) and are handed to Zui as an icon set and a style. Zui keeps only the mechanisms. This answers the open question in Zui's PLAN.html.
D6Widget names for testsKeep BeeModel's record kinds and labels as they are (test contract). Until M10 a bridge copies Zui's record into ui.rec; in M10 the driver, the fuzzers and MCP read Zui's record directly.
D7RendererSoftware renderer only, drawing into BeeModel's buffer. The OpenGL renderer is not used: BeeModel has no GL context (its GPU helper is Vulkan, out of process).
D8Gaps found on the wayFixed in BeeZigUi, with a test there, never worked around in BeeModel. Each fix is listed in Zui's PLAN.html as part of Phase 27.

Milestones

Each milestone ends with the same gate: tests/verify.sh passes (all 315 scenarios, unit tests, the .bee round trip), fuzz.py 200, fuzz_areas.py 100 and fuzz_prefs.py 300 on the debug build show no failures, frame times stay inside the budget (busiest panels ≤ 3 ms, idle frame ≤ 0.7 ms at 1280×800 release), side-by-side screenshots of the moved parts are compared with the previous build, and someone tries it live in a window. The old code of whatever moved is deleted in the same milestone.

Test contract

The widget record is the interface between the UI and everything that checks or drives it: the --shot driver (--click-label, --expect-label, --expect-off, --expect-field, --dump-ui), 315 scenarios, 47 Python tests, six fuzzers, the MCP ui_tree tool and the AI agents. It must not break at any step.

  • Names stay. A moved widget keeps BeeModel's kind and label: a Zui numberField records as number, a menu item as menuitem, a tree row as row, a tile as tile. The bridge holds one mapping table from Zui kinds to BeeModel's ~50 kinds; custom ones (keyrow, swatch, channel, addnode…) are recorded with ui.recordWidget.
  • Hidden is not listed. Zui leaves scrolled-away and covered widgets out of the record. Scenarios that relied on BeeModel listing hidden widgets get a scroll step, never a weaker check.
  • Scenarios do not change to make a step pass. If one must change (a label that was wrong, a widget that moved menus), the change and its reason go in the milestone's notes.
  • New scenarios per step for what Zui adds (keyboard reach of every menu item, disabled reasons, drop refusals).
