Zui plan

An immediate-mode UI library in pure Zig. Phases, demos and status. Target: Zig 0.17.1.

Phases

Each phase ends in something you can run. Tick “Reviewed” once you have looked at it; ticks are saved in this browser.

BeeModel coverage

Phases 13 to 27 are planned from an analysis of beemodel-zip, the Zig port of BeeModel. It is about 72,000 lines and draws its own immediate-mode UI (ui.zig, app.zig, menus.zig, pies.zig, editors.zig, filebrowser.zig, colorpick.zig and others). The analysis also used the original's docs/UI.md, which describes the editors the port has not reached yet. Each row is a kind of UI element BeeModel needs, where BeeModel uses it, how far Zui covers it today, and the phase that closes the gap.

Stays in BeeModel, not Zui: the 3D rasterizer, path tracer and everything drawn inside the viewport (gizmo logic, overlays, sculpt cursors), the operator catalog and its 692 commands, keymap contents and presets, modal G / R / S, and the scene data itself. Zui supplies the widgets and mechanisms; BeeModel supplies the content.

Decisions to confirm

DecisionWhy
Backend before widgetsThe spec puts the backend at step 6. It moved to Phase 1 so that every later step has a demo you can run.
Software rasterizer + SDL3 windowThe rasterizer is pure Zig. SDL3 is the single C dependency, isolated in backends/sdl3.zig, and it covers Linux, Windows and macOS with one backend.
Pure-Zig TrueType, no FreeTypeKeeps the core free of C. No kerning or hinting at first; see Known limits.
Widgets don't return errorstry ui.button(...) on every line is noise. The first allocation failure is latched and returned by ui.endFrame().
Zig 0.17.1 onlyThe spec says 0.13+, but std.Io, the build API and the language all changed since then. Supporting both isn't practical.
Library at the project rootThe spec shows a zui/ folder. The beezigui project root plays that role.
One frame of layout memoryGroups remember last frame’s size, so grow and alignment settle one frame after a change. The library asks for that extra frame itself.
Presses are tested where they happenedSeveral events can arrive between frames. Testing the press position, not the current one, fixed fast drags that live testing showed failing.
Text input edits your bufferui.textInput(name, &buffer, &len, .{}): the caller owns a byte buffer and its length, so editing never allocates. Only undo history and pastes use memory.
Key presses keep their orderInput records each key with how much text had been typed at that moment, so typing, Backspace and typing again within one frame replay correctly.
Focus ring only after keyboard useClicking a widget focuses it so Tab continues from there, but the ring shows only once Tab has been pressed, like a browser's :focus-visible. Custom widgets join the tab order with ui.focusable(id, &result).
Escape undoesIn a text field Escape restores the text from when it got focus; during a slider drag it restores the old value.
Overrides save the whole stylepushColor(.button, c), pushMetric(.rounding, 0) and pushStyle(.light) each save the full style; popStyle restores it. Nothing can leak past a pop, and field names and value types are checked at compile time.
Popups are windowsA popup is a window with no title bar, kept above ordinary windows. It gets the same hit testing, so a click on it never reaches what is underneath. It sizes itself to last frame's content and is hidden on its first frame until that size is known.
The showcase has its own main loopPhase demos share a harness; examples/demo doesn't, so it doubles as the reference for wiring Zui into an app, and it builds as a separate package against Zui by path.
Embedded font: Liberation SansSIL OFL, licence included next to it. About 410 KB, only linked if you use it.
Anti-aliasing by a fringe, shared by both renderersLines and polygons are turned into triangles with a one-pixel band fading to transparent (zui.tessellate). A renderer only fills triangles with blended colours, so software and OpenGL draw the same edges, and a new backend gets anti-aliasing for free.
Images are the app's pixels, cached by id and versionNo upload API: the app owns the pixels, the software renderer reads them directly, and the GL renderer re-uploads only when image.touch() bumped the version. A 3D viewport rendered on the CPU every frame costs one copy.
Shadows skip what covers themBenchmarking Phase 13 showed the Phase 12 window shadows cost about 0.65 ms of a 2.7 ms frame, mostly filling the area under each window. A shadow now knows the opaque shape above it and skips that area, and fades its straight edges a row at a time: 2.3 ms. The UI pass grew from 21 to 31 µs with kerning and the new features.
Scripts name widgets, never coordinatesA script says click Tools > button:Save, and the player looks the widget up in the last frame's record, waits for it if it isn't shown yet, and clicks a point of it that no window in front covers. Layout changes don't break scripts, and a covered widget is reported instead of clicking whatever is on top.
Hidden means not listedThe record holds only what can be seen: clipped to its scroll area or window, nothing in a popup's invisible first frame, nothing scrolled away. An agent reading it sees what a person sees.
The dock layout is the app's datazui.Dock is a fixed-size tree the app owns and copies freely: one per workspace, saved in its own files. Zui lays it out, draws headers and handles drags; the app draws each editor. A new or closed area is reported, so the app keeps per-area state (a viewport's camera) itself.
Scripts wait for the layout to settleLayout uses the previous frame's sizes, so a new panel moves for a frame. The script player now runs frames while the UI asks for one before looking a widget up, as the window loop would; this fixed clicks landing where a button had been a frame earlier.
A modal dialog is the front window that takes every positionHit testing already walks windows front to back; a dialog shown last frame simply answers for every point, so nothing behind it can be hovered or pressed, custom widgets included. Its scope keeps Tab inside for the whole frame.
Fixed: filling rows could only growA group's natural size counted the space its fill items had stretched into, so a .fill row never gave it back and an item after a spacer stayed pushed out of view (found with the status bar's job chip). Groups now ask only for what their content needs.
Selection is a slice of bools the app ownsOne bool per row, kept up to date by the list: fast for thousands of rows, trivially saved or tested, and the app's own code (delete, reparent) reads it directly. The anchor, cursor and rename text live in a small ListState per list.
Drop targets ask, Zui showsA drop zone only reports the drag over it; the app decides, says why with dropHint or refuseDrop, and acts on released. Zui draws the highlight, the label at the pointer and the pointer shape, so every list and canvas drags alike.
Logs are fixed memory, views are virtualLogBuffer allocates once and drops its oldest lines; a text view takes any source with len and line, draws only the lines in view, and tells the scroll area the exact height. 100,000 lines cost what a screenful does.
Fixed while building lists and textsetFocus during a press no longer loses to the press; a field that only uses editField must still call focusable to keep its focus (rename in rows); the Tab scope is set for the next frame, so a dialog or the active area keeps Tab from the first widget on.
Fixed: filling across could only growThe twin of the Phase 18 fix, on the other axis: a group's width counted what its .fill children had been stretched to, so a column that was ever wide stayed wide (found with the colour picker in a 290-unit column). Layouts now also measure the natural cross size, and groups ask for that.
The eyedropper asks the backend for one pixelZui can't read the screen, and shouldn't: while the eyedropper is out, ui.sample_request names a point, and the backend reads that pixel after rendering (pixelAt in both renderers) and passes it to input.onColorSample. The demo harness does it; scripts too. The click that takes the colour reaches no widget.
UI scale is the UI's own zoomui.setScale(1.5) divides the window into fewer, bigger units and multiplies the renderer's scale (ui.renderFrame(display_scale)), so text is rasterized at the new size. Input positions are divided by input.unit_scale; scripts and the record stay in UI units, so they work at any scale.
Themes keep their contrast as they are builttheme.build takes a background, text and accent and derives the rest, moving each colour just far enough to keep 4.5:1 for text and 3:1 for marks; text on the accent is black or white. contrastProblems checks any style; a test runs it over every preset.
Pies and the wheel own the input while openEvery press, key and the wheel go to the menu, and nothing behind it hovers; a quick tap of the opening key reports .tapped, so Z can still toggle X-ray. Key releases are new in Input (keys_down, keys_released), with hold and release in scripts.
2D views: the app keeps where it looksA View2D (origin and zoom per axis) belongs to the app, like the dock layout. The view follows its fit until the user pans or zooms. Handles are described before the background claims the press, so they win, and report a world-unit delta so all selected keys move together; Escape reports the way back.
The node editor reports edits; the graph stays the app'szui_nodes draws and handles nodes, pins, wires, knots and frames, and returns a list of edits (move, select, link, unlink, add, reroute, delete, copy, paste, commit). Nodes are zoomed by drawing them in Style.scaled(zoom), so text stays sharp. An input shows its field by last frame's links; the editor asks for one more frame when they change.
The file browser reads through a Sourcezui_files lists and reads through a small interface: DiskSource for std.Io, or anything else (tests use a fake tree). Previews decode PNG with std.compress.flate; the app supplies thumbnails for its own types and an options panel. Free space comes from statfs on Linux.
Add-ons use only the public APIBoth add-ons build as their own modules on zui, cross-compile for Windows and macOS, and needed only three small public additions: Style.scaled, Ui.regionSize and a compact colorEdit.
Native backends speak the protocols themselvesThe Wayland backend is the wire protocol over a socket with raw syscalls, as BeeModel's is (its design, made a self-contained struct); the Win32 one declares its few system functions itself. No libc, libwayland or libxkbcommon: the demo is one static binary. SDL3 stays for macOS and for apps that want it.
Keys follow the layout, from the keymapThe keyboard layout comes from the compositor's XKB keymap: text with dead keys and AltGr, and Zui keys by the character a key types, so shortcuts follow the label on the key. Trying it live showed why it must be the keymap and not the key's position: a virtual keyboard (wtype) puts letters where Escape normally is, and writes raw keysyms (0xff09 for Tab).
The window frame is a widget; the system moves the windowui.clientFrame draws the title bar and returns what was asked (move, resize which edges, minimize, maximize, close). Moving and resizing are the compositor's job and need the press that started them, so the backend carries the action out.
A detached window is a viewportA window with .detached = true is drawn into a list of its own at its own (0, 0), with its popups and, while the pointer is in it, tooltips. Hit testing only looks at windows in the OS window the pointer is in (input.viewport), and Tab only at those in the one with the keyboard. Backends open and close OS windows to match ui.viewports().
Fixed: the native loop drew without endEach present asks the compositor for a frame callback, and that callback counted as an event: a loop of frames at the screen's rate. Only input, a new size or scale wake the UI now; a present the compositor wasn't ready for is drawn once more, without the input's settling frames.
Embedding draws into the app's own pixelsSoftwareRenderer.useBuffer with clear = false draws Zui over what the app drew, in its buffer, with no copy. That is how the BeeModel pilot works: its canvas, its events, its draw pass.
The BeeModel pilot: one dialog, behind a flagBeeModel's Preferences are Zui's with -Dzui=true: same place, colours, font and sizes; same widget names in BeeModel's own record, so its 315 scenarios and its fuzzers pass unchanged. Without the flag nothing of Zui is built. Two Zui fixes came from it: a click inside one frame on a number field, and left-aligned button text.
Proposed: Zui supplies mechanisms, BeeModel supplies contentMenus, the palette, pies, docking and themes are generic. BeeModel's operator catalog, keymap presets, theme palettes and editor logic stay in BeeModel and feed them. This keeps Zui usable by other apps.
Proposed: the app owns the dataLists, trees, the outliner and node graphs read the app's data each frame and report edits (selected, renamed, moved, linked). Zui never stores a copy of the scene. This is how BeeModel works today.
Proposed: widget record comes early (Phase 14)BeeModel's 47 scenarios, its fuzzers and its MCP ui_tree tool drive the UI by widget name. If Zui has this before the big widget phases, every later phase is tested the same way.
Proposed: big widgets as add-on modulesThe node editor (zui_nodes) and the file browser (zui_files) use only Zui's public API. That proves the API is enough and keeps the core small. Docking lives in the core because it touches hit testing and window order.
Proposed: native backends late (Phase 26)BeeModel already owns its window through its own Wayland code. It can feed Zui's input and show the software renderer's pixels from the first phase on, the way render_png uses Zui without a window. A native Wayland backend in Zui is only needed for other apps.
Undo works from commits, not snapshots at startA widget changes the value in the same frame it reports started, so an app can't copy the state "before" at that moment. Instead it keeps a copy as of the last committed and pushes that copy at the next one. started remains for previews; cancelled means the widget already put the value back.
Disabled is a scope, not a widget optionpushDisabled(reason) covers any number of widgets, custom ones included, with one reason. It fades through the style, so new widgets need no code for it; a null reason keeps the call unconditional.
Proposed: one undo step per editBeeModel's rule is that a drag, a typed value or a toggle is one undo step. Every value widget therefore reports started / changed / committed / cancelled (Phase 15). Apps take their undo snapshot on commit.

Open questions

  • Windows and macOS can only be compile-checked here. Someone needs to run them on real machines, including run.ps1.
  • Should -Dsdl=source become the default? It needs no installed SDL, but the first build fetches and compiles SDL (about 30 s here).
  • Is BeeModel meant to move onto Zui (the Phase 27 pilot), or should Zui only be able to? If it moves, Zui's default look should come close to BeeModel's, so screenshots can be compared.
  • Should Zui ship BeeModel's 114 icons and nine theme palettes as an optional pack, or only the mechanisms to load them?
